## Models inside the APK (user request)

`./gradlew :spike:assembleSherpa1Release -Plectrice.bundleModels=true` packs both bundles from
`../lectrice/models/` into the APK. Off by default: the normal build has no model assets and no copy code.

- `PackBundledModels` (in `spike/build.gradle.kts`) takes the files the English engine reads (the same list as
  `push-model.sh`: model, `voices.bin`, `tokens.txt`, the two English lexicons, `espeak-ng-data`), stores each distinct
  file once as `assets/models/files/<sha256>.bin` (the two bundles share everything except the model), and writes
  `assets/models/manifest.json` (per bundle: path, size, SHA-256 of every file, and a version hash).
  `androidResources.noCompress += "bin"`: all 361 blobs are stored, not deflated; `zipalign -c -P 16` passes.
- Source sets: `src/modelsBundled/kotlin/…/BundledModels.kt` (copy) or `src/modelsPushed/kotlin/…/BundledModels.kt`
  (no-op), chosen by the property.
- First launch: for each bundle, if `files/models/<bundle>/.bundled-version` matches and every file has its size, skip;
  otherwise copy into `<bundle>.partial/`, checking each file's size and SHA-256 while copying, write the marker, then
  rename into place. A progress line every 100 MB in the app log. A bundle pushed with `push-model.sh` has no marker, so
  a bundled build replaces it.
- `push-model.sh` still works for the normal build. Also checked on One UI: **adb can write the app's
  `Android/data/<pkg>/files/` folder** (files end up owned by the app), so its main path works without `run-as`.

## Automation over adb (reusable for any phone)

- `MainActivity` (now `singleTop`) takes `am start … --es step <step>` extras: `import` (`--es file <name>` from
  `<external files>/import/`), `engine` (`--es bundle fp32|int8 --ei threads N --es provider cpu|xnnpack|nnapi`), `bench`
  (`--es threadList 2,4,8`), `accelerators` (optional `--ei fp32Threads/int8Threads`), `play`, `soakWhenUnplugged`.
  Every step logs `<step> done` (or `failed`) to logcat tag `LectriceSpike`. One step at a time. The buttons still work.
- **Results moved to the external files folder** (`/sdcard/Android/data/<pkg>/files/results/`), because adb can't read
  internal storage from a release build. The share button still works (`external-files-path`).
- **`spike/run-phone.sh <serial> <large.pdf> <medium.pdf> [threads] [out dir]`**: install, first launch, engine fp32/int8,
  push + import both PDFs, bench (with `dumpsys meminfo` every 20 s), accelerators, engine at the fastest CPU combination,
  Play 2 min, pull the results, then arm the soak. For the S26 Ultra: `spike/run-phone.sh <serial> <large> <medium> 2,4,6,8`.
  Run 2 used it up to the accelerators. Then it stopped at the fastest-combination step (it picked an older result
  file; fixed: it now reads the newest session's file by name). The remaining steps were done by hand with the same
  commands.
- New button **4b Soak when unplugged**: waits until the phone stops charging, waits 60 s more so it can be put down,
  then runs the 10-minute soak and the 5-minute battery runs for any accelerator that earned one this session.

**Verdict so far: the S10+ is red on speed.** Even the best combination makes speech about 1.5–1.8× slower than real
time, so live listening can't keep up. Per §6, the S10+ sets the minimum phone class: **phones like the S10+ get
Prepare-first** (an hour of audio takes about 1.5–1.8 hours to prepare, while charging), and the app says so on the first
run. Memory, import, `get_document`, native loading and APK size all pass. The GO decision itself waits for the S26
Ultra (S5).

Notes for the first-run screen (draft, S10+ class): "fp32: slower than real time on this phone; prepare chapters
ahead"; "int8: much slower on this phone, not recommended".

Other observations:
- More threads don't help past 4: 6 is about the same, 8 is much worse (the A55 little cores hold it back).
- Heat matters a lot: fp32 4t went from 1.46 at 36 °C to 1.78 at 40 °C, and the first 2-thread bench drifted from
  1.36 to 2.54 over its three runs as the phone warmed up.
- `ready_ahead_ms` was always 0 during Play: at RTF > 1 the core's read-ahead never gets ahead. ExoPlayer's own
  preloading and the read-ahead also compete for the one engine.
- Engine load is 1–3 s slower when the phone is hot, and int8 loads slower than fp32.

## Unplugged soak (2026-10-25, over wireless adb)
fp32, 4 threads, cpu, 10 minutes, unplugged, battery 34–35 °C, thermal status ≤ LIGHT the whole time.
- **Sustained RTF 1.22–1.58 while the app was in front** (cooler and unplugged is faster than the
  plugged-in 1.76). Still **red** (limit 0.9): the S10+ class needs Prepare-first.
- Between about 5.5 and 8.5 minutes the app was in the background (the user opened Settings to pair
  wireless debugging) and Samsung throttled it: RTF 4–8 there. So the totals are pessimistic:
  88 sentences, 5.2 audio minutes, 233.5 mAh (≈ 45 mAh per audio minute; battery 84 % → 79 %).
  Background throttling is itself a finding: real generation must run in a foreground service.
- No heat problem: RTF at minute 1 vs minute 10 is about the same.
- Result file: `docs/results/S10plus-sherpa1-soak.json`. Cold engine load after a reboot: not done (optional).
